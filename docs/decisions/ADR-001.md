# ADR-001: Approvals are records, not a boolean field

**Status:** Accepted
**Date:** 2026-09-03

## Problem

Some request types cannot move until someone approves them. A work expense is the obvious
one: the requester asks, a manager agrees, and only then does Finance act.

The first shape most people reach for is a field on the request, `approved: true / false`.
The question is whether that field can carry what the spec is asking of it.

## Options

**A — a boolean on the request.** One column. Trivial to read and write, no extra entity,
no joins, the queue query stays flat.

**B — an Approval entity, one record per decision.** Each record names the request, the
deciding employee, the decision, the time, and a reason if there is one. Zero, one or
several per request.

## Decision

B.

A boolean cannot answer questions we have already committed to answering. `approved: true`
does not say who, so audit fails. It does not say when, so "how long did this wait on a
manager" is unanswerable. It has nowhere to put a rejection reason, which forces a second
field and then a third.

## Consequences

**Better.** Audit works, since every approval names a person and a time. Rejection becomes
a normal recorded decision instead of a special case.

**Worse.** One more entity. "Is this approved" becomes a query over related records
instead of reading a column, so the logic guarding the IN_PROGRESS transition has real
work to do.

**Commits us to.** Approval state is derived from approval records and never stored a
second time alongside them. If both existed they would eventually disagree and nobody
could say which was right.
